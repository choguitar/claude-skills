# 상황별 흐름

## 1. 코드·가사 텍스트를 받았을 때
1. 받은 내용을 format.md 형식으로 정리해 임시 txt로 저장한다. 섹션명은 표준 이름으로 고친다. 코드·가사는 바꾸지 않는다 — 오타처럼 보여도 사용자에게 묻는다.
2. 출력 방식을 사용자에게 묻는다: **새 파일** 또는 **기존 악보에 추가**(`--append-to`). 사용자가 이미 말했으면 묻지 않는다.
3. 빌드 → 검증(layout.md) → 결과 보고.

`--append-to`는 기존 악보 내용을 건드리지 않고 뒤에 붙이므로, 사용자가 Word에서 고친 내용도 그대로 남는다.

## 2. 이 스킬로 만든 악보의 곡을 고칠 때
1. 현재 docx에서 `extract.py`로 txt를 새로 뽑는다 — 사용자가 Word에서 고친 내용이 반영된 상태에서 시작하기 위해서다. 예전에 쓴 txt는 쓰지 않는다.
2. 요청대로 txt를 고친다.
3. 빌드 → 검증. 결과는 새 파일로 쓰고, 원본을 바꿀지는 사용자에게 맡긴다.

Word에서 손으로 바꾼 자간 같은 세부 서식은 이 과정에서 빌드가 다시 계산한다.

## 3. 예전 서식 악보 docx를 받았을 때
1. `extract.py`로 txt를 뽑는다. build.py로 만든 파일은 스타일로, 그 외 파일은 내용(굵은 16pt 이상 = 제목 등)으로 구분한다.
2. 출력된 `[확인 필요]` 목록을 사용자에게 보여준다. 곡 정보 줄이 없던 곡은 **마지막 코드로 Key를 추정**했을 뿐이라 틀릴 수 있다.
3. 뽑은 txt의 섹션명을 표준 이름으로 고친다(`grep -h '^\[' OUT.txt | sort | uniq -c` 로 종류부터 확인).
4. 빌드 → 검증. 원본 docx는 덮어쓰지 않는다.

`--append-to`는 build.py로 만든 파일에만 쓸 수 있다. 예전 서식 파일에 곡을 추가하려면 먼저 이 흐름으로 변환한다.

## 4. 곡 제목만 받았을 때
가사·코드를 기억으로 채우지 않는다. 가사는 저작물이고, 기억으로 쓴 코드는 틀리기 쉬워서 합주 현장에서 문제가 된다.
제목·곡 정보·섹션 틀만 담은 txt를 만들고, 코드와 가사를 붙여넣어 달라고 요청한다. 받으면 흐름 1로 간다.

## 결과 보고 때 알릴 것

- 폰트 없는 PC·맥에서 열 파일이면: 폰트가 설치된 Word에서 **한 번 열어 저장**해야 D2Coding이 파일에 포함된다(포함 설정은 켜져 있고, 실제 포함은 Word가 저장할 때 한다). Word는 **문서에 쓰인 글자만** 포함하므로, 폰트 없는 PC에서 보기·인쇄는 되지만 새 가사를 입력하면 그 글자는 다른 폰트로 나온다 — 편집할 PC에는 폰트를 설치한다. 배포·인쇄는 PDF가 가장 안전하다.
- Word 스타일로도 직접 편집할 수 있다: `악보 제목` → `곡 정보` → `섹션` → `코드` → `가사` 순서로 Enter 시 자동 전환. 코드 줄은 **반 마디마다 Tab 한 번** — 코드 1개 마디는 `|B` Tab Tab, 2개 마디는 `|E` Tab `F#` Tab. 넘치는 마디는 문자 스타일 `코드 좁게`.
